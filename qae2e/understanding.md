## What it is

QAE2E is an **end-to-end agentic QA platform** (inspired by [Idrikta](https://www.idrikta.com)'s flow):
from a **product requirement document** (PRD) all the way to **running the newly generated test cases**
in a real DevOps environment. A suite of specialist AI agents orchestrates the whole pipeline.

Tagline: **"AI-Powered Quality Engineering. From Requirement to Release Confidence."**

---

## The end-to-end vision (target architecture)

The complete product the user wants — each stage is a source of requirements, a generation step, an
export/publish target, or a check-in/execution step:

```
SOURCE                           GENERATE                    EXPORT / PUBLISH        CHECK-IN / EXECUTE
┌──────────────┐          ┌──────────────────┐          ┌──────────────────┐       ┌────────────────────┐
│ Jira (by ID) │──┐       │  RI agent        │          │ Zephyr (Scale)   │       │ GitHub repo        │
│ Confluence   │──┤       │  MT agent        │          │ TestRail         │       │  (existing         │
│  (page ID)   │──┼───▶   │  AS agent        │───▶      │ CSV / XLSX       │───▶   │   automation       │
│ Figma (image)│──┤       │  EX + DO agents  │          │  (download)      │       │   framework)       │
│ Manual paste │──┘       │  IQ agent        │          │  (RAG dedupe:    │       │  → new branch      │
└──────────────┘          └──────────────────┘          │   Pinecone +     │       │  → run in local    │
                                                        │   free embed)    │       │    Docker          │
                                                        └──────────────────┘       │  → if pass → push  │
                                                                                  │  → Docker / CI     │
                                                                                  │    trigger +        │
                                                                                  │    results posted   │
                                                                                  └────────────────────┘
```

The core idea for test generation: **new test cases are generated by comparing against existing test
cases** (from Zephyr/TestRail via MCP), embedded and stored in a vector store, so we never create
duplicate or "weird" cases. Then automation is checked into GitHub (branch), run locally, verified
passing, and triggered in a real DevOps environment (Docker / CI).

## Findings (2026-08-02)

### Free-model probe: tool-calling works on most free models

`supported_parameters.tools` on the OpenRouter models endpoint is **unreliable** — it reports `false`
for all `:free` models, but a live probe showed **9 of 10 tested free models DO emit `tool_calls`**.
Verified tool-calling free models:

| Model | Notes |
|---|---|
| `nvidia/nemotron-3-ultra-550b-a55b:free` | **Default.** 550B, 65536 max tokens, clean tool calls, best for long test/script output |
| `openai/gpt-oss-20b:free` | Clean tool calls, solid for RI/IQ reasoning |
| `google/gemma-4-26b-a4b-it:free` | Works (previous default) |
| `inclusionai/ling-3.0-flash:free` | Fast, tool calls OK |
| `cohere/north-mini-code:free` | Code-oriented, tool calls OK |
| `poolside/laguna-s-2.1:free` / `poolside/laguna-xs-2.1:free` | Tool calls OK |
| `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free` | Tool calls OK |
| `nvidia/nemotron-3-super-120b-a12b:free` | Can emit duplicate tool calls (noisier) |
| `google/gemma-4-31b-it:free` | 429 rate-limited during probe (inconclusive) |

Full annotated list in `.env.example`. Probe script: `scripts/probe-free-models.mjs`.

### Transient OpenRouter errors surfaced, not cryptic

OpenRouter sometimes 200s with `{ error: {...} }` (provider down / free model out of capacity) or an
empty `choices` array. The old code did `res.choices[0]` and crashed with the opaque
"Cannot read properties of undefined (reading '0')". `lib/llm/openrouter.ts` now validates the response
and throws a readable `LlmError` with the provider's message.

### Pipeline UX: one intake form, then all 6 agents run live

The workspace "Run pipeline" button previously ran **only the Requirement Intelligence agent** (the
6-agent orchestrator existed as dead code). Now:

- **One-shot intake form** (`components/workspace/PipelineSetup.tsx`) — shown in the Connect step before
  running. Collects everything up front in a single collapsible card: source key/ID, GitHub
  token/owner/repo, Jira project key, TestRail run ID, Docker image. **All optional** — skip everything
  and the pipeline still runs end-to-end on local results (the requirement text is always converted into
  full automation; publishing/check-in is the user's choice).
- **Run the 6-agent pipeline** → `POST /api/pipeline` runs `orchestrate()`: RI → MT → AS → EX → DO → IQ
  sequentially on one shared `requirementId`, streaming NDJSON. Intake values are applied as
  `process.env` overrides for the duration of the run (so AS gets the GitHub creds, EX gets the Jira
  key, etc.) and restored afterwards.
- **"Agent N/6 running" banner** — the runner emits `agent_start` / `agent_done` events (with
  index/total), so the UI always shows which of the six agents is live.
- **Agent workbench** (`AgentStream`) — per-agent expandable cards: status + duration, tool call/result
  pairs streaming live (with a "working…" pulse on the in-flight tool), final agent output, artifact
  badges, per-agent issues, filter tabs, expand/collapse-all, and copy-all-logs.
- **Run summary** (`PipelineSummary`) — after a run, a card shows every agent's status, artifact counts
  (test cases / scripts / defects / tests-run) and a highlighted **Issues** list (Pinecone not
  configured, no scripts generated, tests not run, rate limits).
- **Auto-healing test run** — after the AS agent generates scripts, the orchestrator materializes them
  to a temp dir, runs them in a local Docker container, and if tests fail the **LLM fixes the failing
  files and re-runs** (up to 3 attempts). Real results are recorded on a real cycle. Status events
  stream so the UI shows "Running generated tests in Docker…" / "Tests passed after N attempt(s)".
- **No fabricated execution** — EX and DO are strictly forbidden from simulating test results. EX/DO
  record **only** real results provided to them (from the Docker autofix run) onto the real cycle; if
  no Docker run happened, they report "tests were not run" instead of inventing pass/fail evidence,
  screenshots, or CI build numbers. If an agent errors (e.g. LLM rate limit), the pipeline **stops** and
  downstream agents show as skipped rather than producing misleading output on bad input.
- **Run history + ZIP download** — every pipeline run is saved (events, generated code, test
  results) to **Vercel Postgres** (`qae2e_runs` table) when `POSTGRES_URL` is set, or `data/runs.json`
  locally. The **Run history** panel (right rail) lists runs and downloads a **ZIP bundle** — generated
  Playwright code, `run.log`, `test-results.json`, and a summary README — so the automation is
  retrievable even when GitHub isn't connected. (Vercel-compatible: no filesystem writes in prod.)
- **Collapsed DevOps section** — "Check in & run (GitHub + Docker)" is a collapsible card at the end of
  the left column (was inline mid-page): `GitHubCheckin` + `TestRunner` expand on demand.

Both the requirement and every artifact persist server-side first, linked by `requirementId`; the right
rail (TraceabilityRail, ReleaseGauge) populates live as artifacts appear. Connectors are used when
configured; with none configured the pipeline still runs to local results (manual source).

## The complete end-to-end flow (the product being built)

### Stage 1 — Connect a source (pick one)
- **Jira**: enter Jira URL, email + API token (or OAuth) → fetch issue by **Jira ID** → requirement text.
- **Confluence**: enter Confluence URL + API token → fetch **page by page ID** → document content.
- **Figma / image**: connect Figma (Figma REST API token) to pull a design/frame, or upload/paste an image
  of the requirements → extract text via vision/OCR (free model).
- **Manual**: no connection needed — paste the PRD text directly.
- The UI asks **which tool**, tells the user **exactly what credentials are required** (token, username,
  password, URL), shows connection status, and **surfaces any missing credential directly in the UI**.
- **Credentials today**: none are hardcoded. The user has no live Jira/Confluence/TestRail credentials yet
  — the UI prompts for them and the user will provide real (or free-trial) credentials later for testing.

### Stage 2 — Generate test cases (with RAG dedupe)
- RI analyzes the requirement; MT generates cases.
- **Before generating**: pull existing test cases from **Zephyr or TestRail** (via MCP), embed them
  (free embedding model — no API cost), store in a vector store (**Pinecone free serverless tier**, the
  user provides the Pinecone API key).
- New cases are generated **by comparing with the existing corpus** → no duplicates, no irrelevant cases.
- **Output**: editable test cases, review before finalizing.

### Stage 3 — Publish / export the cases
- Choose: publish to **Zephyr**, publish to **TestRail**, or export to **CSV / XLSX** (downloadable).
- Saved to the store, downloadable from the workspace.

### Stage 4 — Check in the automation (GitHub)
- User connects **GitHub** (fine-grained PAT) and provides the **existing automation repo** (framework).
- QAE2E **reads the existing framework** and existing test code.
- LLM generates automation for the **new** test cases in that framework's style.
- Creates a **new branch** in that repo, adds the new test automation locally.
- **Runs all tests locally** (the app clones + installs + runs). If they pass → commit to the new branch.
- If no repo provided → generate the code locally as files and tell the user "these are the test cases /
  this is the automation" (no push).

### Stage 5 — DevOps execution
- **Primary: local Docker.** The user starts Docker on their machine; clicking "run tests" triggers the
  suite in a local Docker container. (GitHub Actions / Jenkins remains an optional later path.)
- The full branch's test suite runs in that environment.
- **Results are posted back**: pass/fail evidence linked to the cycle, defects raised, results to
  Jira/TestRail as configured.

## Core principles

- **Free models only** — never use paid OpenRouter models. Hard guard: `assertFreeModel()` refuses any
  model without `:free`.
- **MCP-shaped tools** — every connector/integration is an MCP-shaped tool
  (`{ name, description, inputSchema, handler }`), so the same handler serves the web UI **and** external
  MCP clients.
- **Traceability by design** — every artifact links to one `requirementId`.
- **Test generation is grounded** — compare against existing cases from Zephyr/TestRail via RAG
  (Pinecone free serverless + free embedding), never generate blind duplicates.
- **Credentials surfaced, never hardcoded** — the UI tells the user exactly what each connector needs and
  prompts for it; no secrets in the repo.
